## 🧪 실험3: 기물 이동 시 조건문 폭발

### 📝 해볼 것

코드를 작성하지 않고, 설계만 해본다.

1. 각 기물(차, 마, 상, 사, 장, 포, 졸)의 이동 규칙을 나열
2. 이동 가능 여부를 if/switch로 작성한다고 가정
3. 조건문이 몇 개나 필요할지 예상

### 🔎 관찰할 것

- 각 기물별 이동 규칙
  - **궁(왕)**: 궁궐 안에서만 움직일 수 있음. 방향에 관계 없이 한칸씩 움직일 수 있음. 다른 기물을 뛰어 넘을 수 없음. 시작 위치가 고정되어 있음.
  - **사**: 궁궐 안에서만 움직일 수 있음. 방향에 관계 없이 한칸씩 움직일 수 있음. 다른 기물을 뛰어 넘을 수 없음. 시작 위치가 고정되어 있음.
  - **상**: 한번에 앞/옆/뒤로 1칸, 대각선으로 2칸 움직임. 다른 기물을 뛰어 넘을 수 없음. 시작 위치를 마와 바꿀 수 있음.
  - **마**: 한번에 앞/옆/뒤로 1칸, 대각선으로 1칸 움직임. 다른 기물을 뛰어 넘을 수 없음. 시작 위치를 상과 바꿀 수 있음.
  - **차**: 직선으로 간다면 원하는 만큼 칸을 이동할 수 있음. 다른 기물을 뛰어 넘을 수 없음. 시작 위치가 고정되어 있음.
  - **포**: 포를 제외한 다른 기물을 1개 뛰어 넘거나 잡을 수 있음. 다른 기물을 뛰어 넘을 때만 앞/옆/뒤로 원하는 칸만큼 이동 가능. 시작 위치가 고정되어 있음.
  - **졸/병**: 앞/옆으로만 전진할 수 있음. (뒤/대각선으로 이동 불가) 다른 기물을 뛰어 넘을 수 없음. 시작 위치가 고정되어 있음.

| 항목               | 기록     |
|------------------|:-------|
| 예상되는 조건문 개수      | 18개 이상 |
| 가장 복잡한 기물의 이동 규칙 | 포      |

### 🗂️ LMS+ 제출

- **Q. 설계 초안을 작성해 주세요.**    
  장기판은 '2차원 기물 클래스 배열' 자료구조로 표현하며, 빈 칸은 Enum이나 null로 표현하는 것을 고려하고 있습니다.    
  기물 객체는 기물명, 시작 위치, 이동 가능 조건(규칙), 생존 여부, 점수 정보를 가지게 됩니다.    
  위치 정보의 책임은 둘로 나누어, 변하지 않는 '시작 위치'는 기물이 관리하고, 계속 변하는 '진행 위치'는 보드가 관리하도록 설계할 예정입니다.   


- **Q. 변하는 정보와 변하지 않는 정보를 분류하고, 각 상태의 관리 책임에 대한 의견을 작성해 주세요.**    
  - **변하는 정보(상태)**: 기물의 현재 위치, 생존 여부, 이동 가능/불가능 위치, 승부 종료 시점     
  - **변하지 않는 정보**: 보드의 크기, 기물명, 기물의 시작 위치, 기물 점수    

  상태는 플레이어의 선택에 의해 변경됩니다. 게임의 정상적인 전개를 위해 기물의 위치 및 생존 여부 같은 상태는 외부에 드러나야 한다고 생각합니다.     
  만약 상태가 잘못 관리되면 기물이 갈 수 없는 곳으로 이동하거나 점수가 잘못 반영되는 등 게임 로직 자체에 문제가 생기게 됩니다.     


- **Q. 분석한 기물별 이동 규칙을 정리하고, 예상되는 조건문 개수와 잠재적 문제점을 작성해 주세요.**    
  - 기물별 규칙
    - **궁, 사**: 궁궐 안에서만 방향 상관없이 1칸씩 이동 (뛰어넘기 불가, 시작 위치 고정)
    - **상**: 앞/옆/뒤 1칸 + 대각선 2칸 (뛰어넘기 불가, 마와 위치 변경 가능)
    - **마**: 앞/옆/뒤 1칸 + 대각선 1칸 (뛰어넘기 불가, 상과 위치 변경 가능)
    - **차**: 직선으로 원하는 만큼 이동 (뛰어넘기 불가, 시작 위치 고정)
    - **포**: 포를 제외한 기물을 1개 뛰어넘어서만 앞/옆/뒤 원하는 만큼 이동 (시작 위치 고정)
    - **졸/병**: 앞/옆으로만 1칸 전진 (뛰어넘기 불가, 시작 위치 고정)

  if/switch 문으로 이를 처리한다고 가정하면 최소 18개 이상의 조건문이 필요할 것으로 예상되며, 가장 복잡한 기물은 '포'입니다.    
  이러한 조건문이 한 곳에 모여 있으면 로직이 복잡해져 한눈에 파악하기 어렵고, 이로 인한 조건 누락이 발생하기 쉽습니다.    
  결과적으로 유연한 규칙 변경과 확장이 매우 어려워집니다.    


- **Q. 조건문 없이 처리할 수 있는 구조적 대안에 대한 아이디어를 작성해 주세요.**    
  모든 이동 규칙을 하나의 조건문으로 모아두는 대신, 각 기물의 조건 규칙은 개별 클래스의 구현으로 분리해 관리하는 대안을 생각했습니다.    
  또한, 이동 가능 여부와 같은 동적인 부분은 상태 패턴을 활용해 제어할 계획입니다. 
  이렇게 설계하면 새로운 기물이 추가되거나 기존 규칙이 변경될 때, 해당 기물 클래스의 내부 로직만 수정하면 되므로     
  과다한 분량의 조건문으로 인한 혼란과 확장의 어려움을 해결할 수 있습니다.
